写在前面 / Introduction
 
我是一名非计算机专业的大一学生。在尝试构建完全本地化的 RAG 系统时，为了避开主流的“遗忘曲线”和“记忆压缩”，我采用了极其克制的物理隔离架构。
I am a freshman non-CS student. While building a fully local RAG system, I avoided mainstream "forgetting curves" and adopted a minimalist physical isolation architecture.
 
但在运行过程中，我观测到了一个非常有趣的现象，希望能向社区的大佬们请教探讨。
However, I observed a very interesting phenomenon during operation and would love to discuss it with the community. 
 
现象记录 / The Observation 
 
在一次对话中，系统本轮检索发给大模型的语块仅为 [720, 546, ...]，其中完全不包含 [651] 的原始文本。但大模型在回复时，极其自然地引用了 [651]。
 
这里是奇迹发生的核心：
经过底层排查，我发现 [720] 号语块的原文中，包含了上一轮对话时，大模型自己对 [651] 号语块生成的“总结性引用”（即：上一轮 LLM 写了一段话，句末标了 [651]，随后系统用 !save full 把这段带编号的回答原样存成了 [720]）。
 
大模型在这一轮读取了 [720] 中自带的引用元数据（也就是那个 [651] 标号），自行跨层进行了逻辑回溯，建立了与底层记忆的隐式关联。
 
During a conversation, the retrieved chunks were only [720, 546, ...], which did NOT include the original text of [651]. But the LLM naturally cited [651].
 
Here is the core of the miracle:
After debugging, I found that chunk [720] contained a "summary reference to [651] generated by the LLM itself in the previous round". The LLM read the citation metadata inside [720] and recursively pulled the historical association out of the database by itself.

深度机制揭示：动态滑窗与拓扑死结 / Topological Knot
 
这并非普通的 RAG 跨层检索，而是一个由极其简单的物理机制交织产生的“拓扑死结”。如果你克隆了本项目并喂入真实语料跑上数十轮，你一定会被这个现象震惊：
1. 滑窗内的二次概括：系统每轮提供 7 个生肉语块。大模型在 6000 字符的滑窗内，会对这些生肉进行情境概括（熟肉），并在句末打上引用标号（如 [1024]）。
2. 历史标签包裹性：由于 !save full 全量保存元数据，新提供的生肉中，极大可能包裹着更早之前的引用标号。
3. 拓扑死结（溯源死亡）：当模型输出一个标号时，你根本无法用常规逻辑查清，它究竟来自本轮的 7 个生肉？上一轮的二次概括？还是历史继承的标号？又或者是前面两个现象的反复嵌套？你无法用任何常规 SQL 去 JOIN 出唯一源头。这是一个拓扑意义上的死结。 
(它证明了系统内部完成了类似生物海马体的“记忆重固化”。它不是冷冰冰的 SELECT，它是在用今天的心情去腌制昨天的故事。)

🛠️ 保姆级使用说明 (Step-by-Step Guide)
 
数据准备与初始化 (Data Ingestion)
 
在启动主程序之前，你需要先让你的本地语料变成 real_rag.db。本项目不提供臃肿的建库脚本，只需要几十行极简代码即可完成三表对齐。核心注入逻辑如下：
import apsw, sqlite_vec
from sentence_transformers import SentenceTransformer

# 1. 连接数据库并加载向量扩展
con = apsw.Connection('real_rag.db')
con.enableloadextension(True); sqlite_vec.load(con); con.enableloadextension(False)
cur = con.cursor()

# 2. 加载本地 BGE-M3 模型
model = SentenceTransformer('./models/bge-m3')

# 3. 模拟你的语料切块
text_chunk = "这是从你的 60 万字日记里切出来的一段话。"
source_tag = "live_2026_11" # 这里就是 [主题: 房间名] 的物理房间号

# 4. 写入主表（底层的触发器会自动同步 FTS 索引）
cur.execute("INSERT INTO chunks (text, source) VALUES (?, ?)", (text_chunk, source_tag))
chunk_id = cur.lastrowid

# 5. 计算 1024 维向量并写入向量表
vector = model.encode(text_chunk).tobytes()
cur.execute("INSERT INTO vec_chunks (chunk_id, embedding) VALUES (?, ?)", (chunk_id, vector))

# 注：批量灌库请务必用 BEGIN / COMMIT 包裹事务。
# 灌库完毕后，记得运行一次 python build_df_cache.py 生成全局词频雷达。
 
核心交互与指令 (Core Commands)
 
1. 终端启动与极致防崩溃分屏
# 启动主程序
python ask.py

# 强烈建议：在另一个终端窗口输入以下命令，开启瀑布流防崩溃监控
tail -f ./chat_stream.log
 
(由于大模型流式输出极快，为防止 macOS 原生终端渲染卡死，本系统将输出流重定向至日志文件。左侧提问，右侧 tail -f 实时查看。)
 
2. 极速输入层：空回车与 Nano 编辑器
• 短文本：在 Observer > 提示符下，直接按下 Enter 键。系统会利用 pbpaste 自动读取剪贴板并发送。
• 万字长文：输入 !edit 唤起 nano 编辑器。写完按 Ctrl+O 保存，Ctrl+X 退出，自动发送。 
3. 物理主题锁定
• 语法格式：[主题: 房间名] 你的真实问题 (⚠️ 右方括号后必须跟一个空格)
• 示例：[主题: system] 之前的架构设计还有什么漏洞？ 
4. 记忆刻录与系统退出
• !save：仅保存上一句输入的原始语块。
• !save full：（极其重要） 保存完整上下文对话及引用元数据，是触发“拓扑死结”的唯一途径。
• 退出：输入 exit 或 quit。 

架构设计特点 / Architecture Highlights

*   **API 网络重试**：原生 `try-except`，断网静默等待 5 秒重试 3 次，防丢数据。
*   **50轮水印重算**：为防 Jieba 分词薛定谔变异，系统在 `!save` 时自动比对语块水印。满 50 块触发 `subprocess` 静默异步重算 `df_cache.json`，前台聊天无感。
*   **并发读写防护**：后台重算时若发生读写冲突导致 JSON 读取异常，系统自动降级为空字典，确保主程序绝不闪退。
*   **数据库触发器**：主表变动，FTS 索引自动静默同步。
*   **1:1 权重平权**：弃用 Rerank，FTS 与 BGE-M3 向量双路召回平权，保留原始语义。
*   **引用正则校验**：实时审计大模型生成的 `[编号]`，不仅是防御幻觉，更是观测“隐式拓扑”的物理探针。
